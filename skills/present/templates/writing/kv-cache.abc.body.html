How to read this page

Each block below explains the same thing: the KV cache, the memory where a language model keeps the keys and values (K, V) of earlier tokens so it does not recompute them for every new token. Only the register changes. The numbers come from the Llama 3.1 8B config.json (32 layers, 8 KV heads, head dimension 128, bfloat16).

1 Function

A language model makes text one token at a time. For each new token, the model compares a query with the key of each earlier token. Then it mixes the values of those tokens. The keys and values of earlier tokens do not change. The KV cache keeps them in GPU memory. Thus the model does not calculate them again.

2 Operation without a cache

Without a cache, the model calculates the keys and values of all tokens at each step. At step 100, it calculates 100 rows. At step 1,000, it calculates 1,000 rows. The total work increases with the square of the length.

3 Operation with a cache

With a cache, the model calculates the key and value of the new token only. It adds them to the cache. Then it reads all the rows in the cache. The calculation for each step stays the same. The memory that the model reads at each step increases with the length.

4 Phases

Prefill. The model reads the full prompt in one operation. It fills the cache. The speed of the arithmetic units sets the time.

Decode. The model makes one token at each step. It reads the full cache at each step. The memory bandwidth sets the time.

5 Memory

Each token in the cache uses this quantity of memory: 2 × layers × KV heads × head dimension × bytes for each value. For Llama 3.1 8B, the result is 2 × 32 × 8 × 128 × 2 = 131,072 bytes (128 KiB). A sequence of 8,192 tokens uses 1 GiB. A sequence of 131,072 tokens uses 16 GiB. This is about the same as the memory for the model weights.

6 Procedure: decrease the cache memory

Caution

Calculate the cache memory before you increase the batch size or the sequence length. If the cache does not fit, the server must stop some sequences and calculate them again later.

  1. Use a model with fewer KV heads (GQA or MQA).
  2. Keep the cache in 8-bit floating point (FP8). This decreases the cache memory by 50%.
  3. Use paged allocation, for example vLLM PagedAttention. This prevents unused gaps in memory.
  4. Share the cache between prompts that start with the same text (prefix caching).

In one line: the KV cache trades GPU memory for speed. The model stores each token's keys and values once and reuses them on every later step.

Why it exists

A model generates one token per step. Each new token has to attend to every earlier token, which means it needs their keys and values. Those never change once computed. So the model computes them once and keeps them in GPU memory.

What it saves

Without the cache, step 1,000 recomputes 1,000 rows of keys and values, and total work grows with the square of the length. With the cache, each step computes one new row and appends it. Attention still reads every cached row, so the reading cost still grows with length.

Prefill vs decode

Prefill processes the whole prompt at once and fills the cache; it is limited by arithmetic speed (compute-bound). Decode adds one token per step and re-reads the whole cache each time; it is limited by memory bandwidth (memory-bound). That split is why the two phases tune differently.

What it costs

Per token: 2 × layers × KV heads × head dim × bytes. For Llama 3.1 8B that is 2 × 32 × 8 × 128 × 2 = 128 KiB. An 8K-token sequence holds 1 GiB; a 128K-token sequence holds 16 GiB, about as much as the bf16 weights. Multiply by the batch size for the whole server.

Four levers

  • Fewer KV heads (GQA / MQA). Llama 3.1 8B already uses 8 instead of 32, a 4× saving.
  • FP8 cache. One byte per value instead of two halves the memory.
  • Paged allocation (vLLM PagedAttention). Fixed-size blocks, so memory does not fragment.
  • Prefix caching. Prompts that share a prefix share its cache blocks.

Autoregressive decoding emits one token per forward pass, and each pass needs attention over every prior position — i.e. the K and V projections of all earlier tokens. Those projections are deterministic given the prefix, so recomputing them every step is pure waste: without a cache, step t redoes t rows and total projection work over a sequence grows as O(n²); with one, each step projects a single row and appends it, while attention still scans all t cached rows. That asymmetry splits inference into two regimes — prefill, which processes the prompt in parallel and is compute-bound, and decode, which is memory-bandwidth-bound because every step streams the full cache from HBM (the GPU's on-package memory).

The bill is memory, linear in sequence length × batch: 2 · L · Hkv · dhead · bytes per token. Llama 3.1 8B (L = 32, Hkv = 8 via GQA, d = 128, bf16) lands at 128 KiB/token — 1 GiB at 8K context, 16 GiB at 128K, roughly the size of the weights themselves; without GQA it would be 4× that. The standard levers are fewer KV heads, an FP8 cache (½), paged block allocation to kill fragmentation (vLLM's PagedAttention), and prefix caching so identical prompt heads share blocks.
